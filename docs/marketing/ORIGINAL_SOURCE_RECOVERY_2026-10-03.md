# Preserved pre-editorial photo recovery — October 3, 2026

Problem observed in actual production QA after PR182: selecting a previously branded draft image added another emblem/frame on top. The selected source remained preserved, but this was an easy way for the marketing team to degrade the brand.

Implementation: the owner preview automatically requests a verified preserved source for keys under studio/render-receipts. The authenticated read route first checks the selected editable post/slide. A bounded resolver follows at most eight attached editorial receipts; each link requires the server-associated output hash, source hash, exact metadata parent and editorial method. It rejects cycles, missing/pending receipts, changed bytes/metadata and unrecorded editorial overlays. It stops at the photo before recorded editorial transformations, preserving photographic/AI enhancement history. This is not logo detection and does not claim that the preserved photo contains no pre-existing logo.

The browser hashes the returned source again, normalizes it and composes once. Its preview explains what was recovered and requires inspection. Only explicit Use saves. The unchanged top-level save contract carries the selected-current key/hash/depth inside declared options. The server independently resolves that history, verifies it, and uses the selected-current key for conditional attachment while storing the actual composition source. It rechecks recovery after storage readback. Stable request identity and recovery declaration remain fingerprint-bound; arbitrary declarations cannot authorize a source swap. Attachment resets audit/schedule, retains slide order/count and original storage objects. No trust, publishing, credentials or migration changes.

Evidence: 41 focused tests and 3,429 application tests pass; lint and Functions build exit successfully.
